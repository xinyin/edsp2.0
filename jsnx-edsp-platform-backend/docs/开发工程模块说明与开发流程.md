# 外部数据平台开发工程模块说明与开发流程

## 1. 工程定位

EDSP 2.0 后端采用“平台公共服务 + 独立数据应用 + 服务化公共能力”的结构。每个数据源拥有独立 JVM、端口、日志和发布生命周期；生产链路不经过承载所有业务的集中式 Runtime，公共实现由 `jsnx-edsp-capability-runtime` 独立部署。

核心原则：

- Gateway 只负责统一入口、认证、日志和明确路由。
- Admin 负责配置、审批、授权、计费和发布计划。
- 数据应用负责本数据源的协议适配、上游调用和业务编排；公共转换、安全和响应能力由 `capability-runtime` 承担。
- 普通接口优先配置化，特殊接口才新增 Java 代码。
- 数据应用之间禁止 Maven 互相依赖。
- MySQL 保存平台配置和发布快照，Kafka 承担异步日志和消息，Nacos 承担配置治理。

## 2. 工程目录

```text
jsnx-edsp-platform-backend/
├── common-components/                  # 稳定契约与服务内部实现 JAR
│   ├── jsnx-edsp-contracts             # 稳定请求响应契约
│   ├── jsnx-edsp-client-sdk            # 能力服务及上游调用客户端
│   ├── jsnx-edsp-transform-core        # 字段转换
│   ├── jsnx-edsp-crypto-core           # 加解密和脱敏
│   ├── jsnx-edsp-signature-core        # 签名验签
│   ├── jsnx-edsp-response-core         # 统一响应
│   ├── jsnx-edsp-log-core              # Trace、日志事件和异步队列
│   ├── jsnx-edsp-plan-core             # 发布计划和热切换
│   └── jsnx-edsp-platform-core         # 平台管理领域服务
├── platform-services/                  # 平台公共微服务
│   ├── jsnx-edsp-data-gateway          # 8080
│   ├── jsnx-edsp-data-admin            # 8081
│   ├── jsnx-edsp-data-observability    # 8083
│   ├── jsnx-edsp-esb-adapter           # 8084
│   └── jsnx-edsp-capability-runtime    # 8091
├── data-applications/                  # 按数据源隔离的业务应用
│   ├── jsnx-edsp-data-enterprise       # 8181
│   └── jsnx-edsp-data-credit           # 8182
└── pom.xml                             # Maven/IDEA 唯一聚合入口
```

前端、供应商模拟应用和部署脚本为同级独立工程，不加入后端 Maven 聚合工程。

## 3. 公共组件职责

| 模块 | 承接功能 | 使用方 |
| --- | --- | --- |
| `jsnx-edsp-contracts` | 稳定的请求、响应和 Trace 契约 | 数据应用、能力服务 |
| `jsnx-edsp-client-sdk` | 调用公共能力服务和供应商 HTTP 接口 | 数据应用 |
| `jsnx-edsp-transform-core` | 点号路径读写、直接映射、默认值、常量和基础转换 | Capability Runtime、Admin |
| `jsnx-edsp-crypto-core` | 加解密、Base64、脱敏、密钥引用 | Capability Runtime |
| `jsnx-edsp-signature-core` | 签名、验签、时间戳、字段排序 | Capability Runtime |
| `jsnx-edsp-response-core` | 平台统一返回结构、返回码和结果状态 | Capability Runtime |
| `jsnx-edsp-log-core` | Trace、日志事件、脱敏和非阻塞有界队列 | Gateway、Observability |
| `jsnx-edsp-plan-core` | 发布计划、字段映射、版本缓存和切换 | Capability Runtime |
| `jsnx-edsp-platform-core` | 服务商、数据源、API、审批、授权、计费和 MySQL | Admin、Observability |

数据应用只引入 `contracts` 和 `client-sdk`，不直接引入易变的能力实现 Core 或包含数据库逻辑的 `platform-core`。

## 4. 平台微服务职责

### 4.1 Gateway（8080）

- 统一接收行内调用。
- 调用方认证、API 授权、限流和请求头校验。
- 生成并透传 `X-Trace-Id`。
- 按业务域明确路由到目标数据应用。
- 记录 Gateway 入口、路由、响应和异常日志。
- 使用 `log-core` 有界队列异步发送 Kafka。

示例路由：`/api/v1/enterprise/** → 8181`，`/api/v1/credit/** → 8182`。

不设置 `/api/v1/**` 到集中式服务的通用兜底路由。

### 4.2 Admin（8081）

- 登录和工作台看板。
- 数据服务商、服务商账号和权限管理。
- 数据源和 API 定义管理。
- 请求映射、响应标准化和统一返回码。
- 加解密、签名和安全策略配置。
- 上游、平台和端到端联调。
- 接口发布审批、调用方授权和计量计费。
- MySQL 持久化发布计划快照，并通知 `capability-runtime` 刷新对应接口计划。

### 4.3 Observability（8083）

- 调用日志查询、Trace 链路和节点详情。
- 成功、失败和慢调用分析。
- Gateway、数据应用和上游耗时统计。
- 监控点和告警。
- 后续消费 Kafka 日志并落地明细。

### 4.4 ESB Adapter（8084）

- ESB XML、队列和 HTTP 协议适配。
- ESB 报文解析和响应回写。
- 调用 Gateway。

ESB Adapter 不负责供应商字段映射、加解密、签名和统一返回码。

## 5. 独立数据应用职责

### 5.1 企业数据应用

模块：`jsnx-edsp-data-enterprise`，端口 `8181`，数据源编码 `ENTERPRISE`。

承接企业工商接口，完成请求映射、供应商调用、加解密、返回码转换、响应标准化和计划热刷新。

### 5.2 征信数据应用

模块：`jsnx-edsp-data-credit`，端口 `8182`，数据源编码 `CREDIT`。

承接征信接口，职责与企业应用一致，但独立运行、独立扩容和独立发布。

```text
└── src/main/

```

## 6. 依赖规则和通信方式

允许的依赖方向：

- 平台服务依赖公共组件。
- 数据应用依赖公共组件。
- 数据应用之间不互相依赖。

服务间仅通过 HTTP、Kafka、Nacos 和 MySQL 契约通信：

- HTTP：同步业务调用、管理调用和计划刷新。
- Kafka：异步日志、ESB 消息和发布事件。
- Nacos：配置、服务注册和环境治理。
- MySQL：平台配置、审批、授权、计费和发布快照。

## 7. 新增数据源开发流程

### 7.1 供应商准备

准备服务商信息、数据源编码、基础地址、认证方式、接口文档、请求样例、响应样例、返回码和测试账号。

### 7.2 平台基础配置

在 Admin 中依次完成：

```text
新增数据服务商 → 配置服务商账号和权限 → 新增数据源 → 配置数据源编码、协议和目标应用名
```

### 7.3 创建独立数据应用

复制现有数据应用模板，修改 Maven `artifactId`、Spring 应用名、Java 包名、数据源编码、服务端口、上游默认地址和日志标识。引入：

```text
jsnx-edsp-contracts
jsnx-edsp-client-sdk
```

实现数据源专属 Controller 和上游调用，在根 `pom.xml` 中登记模块；执行计划由 `capability-runtime` 统一加载与刷新。

### 7.4 配置接口

在 Admin 配置接口编码、服务路径、上游地址、请求和响应 Schema、请求样例、供应商响应样例、请求映射、响应映射、统一返回码、安全策略和计费规则。

### 7.5 联调和发布

```text
上游连通性测试 → 平台请求转换测试 → 完整端到端测试
→ 接口校验 → 提交审批 → 审批通过
→ MySQL 保存发布计划与线上路由快照
→ 通知所属数据应用刷新 Plan，并通知 Gateway 原子刷新路由
```

计划切换使用原子引用，新请求使用新版本，在途请求继续使用旧版本。

### 7.6 Gateway 和部署配置

不再为每个数据源修改 Gateway YAML。应在数据源管理中登记稳定的行内 VIP：

```text
application_name = jsnx-edsp-data-housing-fund
runtime_url      = http://行内VIP或代理地址
```

接口发布后，`apiCode + Method + Path → runtime_url` 自动进入 Gateway 路由快照。新增应用仍需修改
启动脚本、停止脚本、Nacos 配置、监控点和数据应用 README，但不需要重启 Gateway。

## 8. 普通接口变更流程

请求字段、响应字段、字段名称、上游地址、默认值、返回码及普通加密签名参数变化，原则上不需要修改 Java 代码或重启应用。

```text
编辑草稿 → 保存映射 → 校验 → 联调 → 提交审批 → 审批发布 → 应用热切换
```

## 9. 特殊接口开发流程

以下情况才在对应数据应用中编写 Java 代码：特殊加密或签名、多供应商编排、非 JSON 协议、复杂报文拆分合并、本地数据库查询、复杂重试补偿或供应商结构无法配置化描述。

开发要求：

1. 代码只能放在对应数据应用。
2. 公共能力优先下沉到 Core，不复制到多个应用。
3. 必须补充单元测试和端到端测试。
4. 不修改其他数据应用。
5. 不把特殊逻辑放回 Gateway 或集中式 Runtime。

## 10. 日志和监控流程

```text
TraceGlobalFilter → GatewayLogGlobalFilter → GatewayLogPublisher
→ log-core 有界异步队列 → Kafka → 日志处理应用
```

日志应包含 Trace、调用方、机构、API、数据源、路由、HTTP 状态、耗时、异常和节点状态。Kafka 或日志处理应用异常时，不能影响同步业务请求。

## 11. 本地开发、构建和发布

启动顺序：

```text
MySQL → 供应商 Demo → Admin → 数据应用 → Observability → ESB Adapter → Gateway
```

统一启动：

```bash
cd /Users/tommy/Documents/外部数据/demo/jsnx-edsp-deployment
./bin/start-vendor.sh
./bin/start-platform.sh
```

后端测试和打包：

```bash
cd /Users/tommy/Documents/外部数据/demo/jsnx-edsp-platform-backend
mvn clean test
mvn clean package -DskipTests
```

单独构建数据应用：

```bash
mvn -pl data-applications/jsnx-edsp-data-enterprise -am package
```

- [ ] 新模块已登记根 `pom.xml`。
- [ ] 数据应用没有依赖其他数据应用。
- [ ] 仅引入 `contracts` 和 `client-sdk`。
- [ ] 所属数据应用能加载和刷新该接口计划。
- [ ] 数据源编码、应用名和 `runtime_url` 已登记。
- [ ] `apiCode` 与 `Method + Path` 在已发布路由中唯一。
- [ ] 请求、响应、返回码和安全策略已配置。
- [ ] 上游、平台和端到端测试通过。
- [ ] 发布完成并验证数据应用 Plan 与 Gateway 路由版本一致。
- [ ] 健康检查、日志、监控和告警验证通过。

## 13. 故障边界

```text
企业应用停止       → 只影响企业接口
征信应用停止       → 只影响征信接口
Kafka 停止         → 允许日志丢失，不影响同步请求
Observability 停止 → 不影响业务主链路
Admin 停止         → 已加载计划的数据应用仍可处理已发布接口
Gateway 停止       → 统一入口不可用，需要 Gateway 集群保障
```

平台的核心隔离边界是“一个数据源一个独立数据应用”，而不是把所有业务转换集中到一个 Runtime 中。
