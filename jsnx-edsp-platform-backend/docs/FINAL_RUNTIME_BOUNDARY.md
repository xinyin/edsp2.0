# EDSP 2.0 最终运行边界

## 结论

生产环境不部署承载所有数据源业务逻辑或转换开销的集中式 Runtime。计划加载、标准化、安全处理、
统一返回和上游调用均在所属数据源应用内完成；各数据源应用独立 JVM、独立发布、独立故障边界。

## 生产调用链

```text
下游系统
  ↓
jsnx-edsp-data-gateway :8080
  ↓ apiCode + Method + Path 查询本地发布路由快照
数据源应用行内 VIP
  ↓ /internal/adapter/published
所属数据源应用 LocalPlanRuntime
  ↓
上游供应商
```

Gateway 只负责统一入口能力：认证、授权、限流、动态路由、Trace 初始化和异步原始日志。每个数据应用
引入稳定契约与 SDK，负责本数据源的执行计划、协议适配、供应商调用和业务编排。

## 配置发布

Admin 负责草稿、校验和发布；执行计划及线上路由持久化到 MySQL。发布事务提交后，Admin 先通知所属
数据应用拉取计划，再通知 Gateway 刷新路由。Gateway 具有周期自愈刷新；数据应用收到 Gateway 的
`X-Route-Version` 后发现本地版本滞后也会主动补拉。内存仅是运行时缓存，重启后从 MySQL 发布快照恢复。

## 故障边界

- 企业应用停止只影响企业接口，征信应用和 Gateway 仍可运行。
- 某个数据源计划发布失败只影响该数据源，不影响其他数据源。
- Admin、观测服务或异步日志链路异常不应阻断已运行的数据应用主调用链；Gateway 的日志写入采用非阻塞降级策略。
- 未同时匹配 `apiCode + Method + Path` 的调用直接拒绝，不会进入任一数据应用。

## 联调入口

联调使用 Admin 的 `POST /api/interfaces/{id}/test`，分为上游连通性、平台转换和端到端测试。它是管理面测试能力，不是生产流量入口；生产请求始终按数据源路由进入独立数据应用。
