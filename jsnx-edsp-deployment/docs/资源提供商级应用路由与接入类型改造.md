# 资源提供商级应用路由与接入类型改造

日期：2026-10-16。适用目录：`demo`。Java 基线：JDK 17。

## 1. 需求与原实现差异

| 项目 | 原实现 | 本次调整 |
| --- | --- | --- |
| 应用归属 | 数据源保存应用标识、运行地址和监听端口 | 资源提供商维护唯一处理应用，其下多个数据源/API 共用 |
| 供应商接口测试 | 存在由 Admin 直接请求供应商的路径 | Admin 必须先解析提供商处理应用，再调用内部执行入口 |
| 缺少应用路由 | 部分路径可能退回直接请求 | 明确拒绝，不绕过处理应用 |
| 正式调用 | 已有动态接口路由，但目的地址取自数据源 | 通过数据源所属提供商解析处理应用地址 |
| 提供商分类 | 机构类别与技术接入概念混淆 | 保留机构类别，新增 HTTP、数据库、平台微服务、Kafka 接入类型 |
| 新应用工程 | 按数据源编码生成 | 按提供商编码生成、校验归属，生成清单升级为 v2 |
| 启动行为 | 脚本可能回写 LHZX 固定应用地址 | 移除该行为，路由由业务配置维护 |

这里的“一个应用”指一个独立部署单元，可以运行多个实例，不是限制一个 JVM。平台不再按提供商下的数据源数量创建应用。

## 2. 执行链路

### 2.1 数据资源接口验证、草稿编排验证

```text
浏览器 → Admin
           → data_source.provider_id
           → data_provider.runtime_url
           → 提供商处理应用 /internal/adapter/execute
           → ProviderConnector / 内置 HTTP 客户端
           → 外围系统
```

上游接口验证和草稿验证不经过线上 API 授权，这是开发测试入口，但都会经过提供商处理应用。它们不是浏览器或 Admin 直连供应商，也不是要求所有开发测试都先发布才能经过 Gateway。

### 2.2 行内正式调用、线上入口验收

```text
行内系统 XML → ESB 请求队列 → ESB Adapter → Gateway
    → apiCode + Method + Path 匹配本地已发布路由快照
    → data_provider.runtime_url + /internal/adapter/published
    → 提供商应用本地执行计划、转换、安全处理、连接器
    → 外围系统 → 响应标准化 → Adapter → ESB XML 响应
```

Gateway 路由刷新仍采用主动通知和周期拉取；新增数据源/API 不需要新增 Gateway 固定业务前缀。

## 3. 配置与存储

| 内容 | 保存位置 | 用途 |
| --- | --- | --- |
| 提供商接入类型 | MySQL `data_provider.access_mode` | 选择提供商应用内部的连接器 |
| 协议连接参数 | MySQL `data_provider.access_config`（JSON） | 保存连接元信息、受控密钥引用，不保存数据库密码明文 |
| 提供商处理应用 | MySQL `data_provider.application_name` | 一个应用标识不能同时绑定不同提供商 |
| Gateway 访问应用的地址 | MySQL `data_provider.runtime_url` | 本地可用单实例地址；多实例可用行内 VIP/反向代理地址 |
| Java 应用监听端口 | MySQL `data_provider.server_port`，生成后写入 Nacos YAML | 决定新应用监听端口，不等同于 Gateway 访问端口 |
| 数据源基础地址/超时 | MySQL `data_source` | 数据源级接口默认配置，与应用运行路由分开 |
| 接口地址、方法、样例 | MySQL `resource_api` | 供应商 API 契约 |
| 标准服务及映射 | `api_interface`、映射表、`release_plan_snapshot` | 平台对外契约及发布快照 |
| 应用启动配置 | Nacos 对应应用的 Data ID | `spring.application.name`、`server.port`、`edsp.data-application.provider-code` |

旧 `data_source.application_name/runtime_url/server_port` 暂保留为迁移镜像，不作为运行路由读取依据。

提供商连接配置随草稿请求或已发布计划传入应用。修改提供商配置后会通知已发布计划刷新；该通知是尽力而为，不是多实例可靠广播。若通知失败，应对各实例执行刷新后再验收；当前版本没有针对“同一服务版本的连接配置变化”提供可靠重试闭环，不应声称已实现强一致热更新。

## 4. 四类接入的实际支持范围

| 接入类型 | 配置字段 | 当前执行能力 |
| --- | --- | --- |
| HTTP | 基础地址、报文编码；接口级 URL/Method/超时 | 内置 JSON 对象请求/响应；POST、GET、PUT、PATCH、DELETE；GET 参数为标量或标量列表 |
| 数据库 | 类型、Driver、JDBC URL、用户名、密码引用、连接池参数 | 已有配置模型及 ProviderConnector 扩展入口；尚未提供通用 JDBC 查询连接器 |
| 平台微服务 | 服务名 | 已有配置模型及扩展入口；尚未定义服务协议、方法调用及服务发现连接器 |
| Kafka | Broker 列表、安全协议 | 已有配置模型及扩展入口；尚未实现 Topic、消息键、响应关联和超时语义 |

后三类不是“填写配置即可真实调用”。没有安装对应连接器时，应用明确报错，不会偷偷按 HTTP 执行。数据源/API 编辑器当前仍以 HTTP 接口开发为主；数据库查询、Kafka 消息资源的专用开发页面和契约尚待补充。SOAP/XML 供应商接口、HTTP 自定义请求头、顶层 JSON 数组也不能由本次改造推断为已全面支持。

### 自定义连接器

在该提供商应用内实现 `com.jsnx.edsp.sdk.ProviderConnector`：

```java
public final class BankDatabaseConnector implements ProviderConnector {
    public String accessMode() { return "DATABASE"; }
    public Map<String, Object> execute(Map<String, Object> connection,
            String method, String endpoint, Map<String, Object> request,
            String traceId, int timeoutMs) {
        // connection.accessConfig：提供商连接配置。
        // 使用白名单查询模板、绑定参数、受控密钥解析和有界连接池。
        // 必须在连接器实现真实的超时，不应从请求报文拼接任意 SQL。
        throw new UnsupportedOperationException("请实现本提供商查询契约");
    }
}
```

在 `src/main/resources/META-INF/services/com.jsnx.edsp.sdk.ProviderConnector` 中写入实现类全限定名。SDK 通过 Java ServiceLoader 加载；重复的同类协议连接器会拒绝启动。连接器可只部署在需要它的提供商应用内，不增加集中式转发服务。

数据库账号、Kafka SASL 等真实凭据必须由应用侧受控配置解析，不应出现在页面报文、调用日志或 Git 中。插件必须提供超时、连接资源释放、异常转换与独立测试。

## 5. 操作步骤

1. 资源方管理：新增或编辑提供商，选择技术接入类型及参数；机构类别独立选择。
2. 在该提供商的“配置应用路由”登记应用名、Gateway 访问地址、Java 监听端口。
3. 根据需要生成工程并同步 Nacos。生成代码不等于完成编译部署，发布 Nacos 不等于应用已经运行。
4. 新应用使用 `executeForProvider(properties.providerCode(), payload, upstream)` 验证草稿归属。提供商编码必须与 `data_provider.provider_code` 一致。
5. 在该提供商下新增数据源。HTTP 提供商的新数据源向导默认带入提供商基础地址，可以按数据源覆盖。
6. 接入并保存资源 API，原始接口测试可选。测试时未配置应用路由会立即拒绝；应用未运行时会得到连接失败，不回退直连。
7. 选择已保存的资源 API 开发标准服务，不要求原始接口先测试通过。保存映射、选做链路验证、发布并授权，再用 ESB/Postman 验收正式链路。

最新的模块职责、资源 API 与标准服务关系及 XML 调用流程，见 [产品模块职责与服务开发流程](产品模块职责与服务开发流程.md)。

## 6. 存量迁移与本地部署边界

- 表结构补齐逻辑位于 `InterfaceService.ensureProviderRoutingColumns()`，在新版 Admin 初始化时执行；初始化 SQL 也已调整。
- 某提供商下旧数据源的应用标识、地址、端口完全一致时，才能自动回填提供商路由。
- 同一提供商下多个旧路由不一致时，不自动任选一个。应先确认唯一处理应用，整合其定制逻辑，再在页面保存提供商路由。
- 模板、工程生成器和 enterprise 样例已改为提供商归属；用户已编写的独立应用不自动覆写。旧应用如果还校验固定 `dataSourceCode`，必须手动升级到提供商归属校验，才能承接同提供商的多个数据源。
- v1 生成清单与 v2 提供商归属不一致时拒绝自动覆盖，避免破坏既有源码。
- 多个提供商历史共用同一应用标识时会触发唯一约束检查，需先拆分。生产迁移前应备份并在测试环境演练，不应直接依赖开发环境自动 DDL。
- 本轮只修改源码和测试，不自动改写现有 MySQL/Nacos 业务配置、不重启当前应用、不影响独立 vendor 服务。已有运行中的旧 Jar 不会因源码变更自动获得新能力。

部署顺序建议：备份 → 确认提供商归属/冲突路由 → 升级各提供商应用并设置 provider-code → 升级 Admin → 刷新 Gateway/计划 → 发布前及线上验收。旧实例与新实例混跑时应先隔离流量，不要直接全栈重载掩盖归属迁移问题。

## 7. 回归点

- 无提供商路由时不直连供应商。
- Admin 实际请求提供商应用的内部入口，并传递 providerCode、dataSourceCode、HTTP 方法、超时和请求体。
- 同一提供商应用接收两个不同数据源；拒绝其他提供商。
- Gateway/ESB 路由查询均从提供商 JOIN 获取地址。
- GET 查询参数实际经本机 HTTP 服务验证。
- 未安装 DATABASE/KAFKA/PLATFORM_SERVICE 连接器时明确拒绝；自定义连接器收到完整配置与请求。
- 发布计划保留 HTTP 方法及提供商连接配置。
- 生成工程归属、Nacos 内容和 JDK17 编译回归。
