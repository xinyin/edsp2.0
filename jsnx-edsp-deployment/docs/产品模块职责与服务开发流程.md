# 外部数据平台：模块职责与服务开发流程

更新日期：2026-10-16。适用于当前 `demo` 工程，Java 基线为 JDK 17。

## 1. 产品对象与归属

```text
资源提供商（例如 raex，独立应用的归属单位）
├─ 数据源 raex-risk
│  ├─ 资源 API：企业风险查询
│  │  ├─ 平台标准服务 A
│  │  └─ 平台标准服务 B
│  └─ 资源 API：个人风险查询
└─ 数据源 raex-relation
   └─ 资源 API：企业关联关系查询
```

资源 API 是供应商原始接口，标准服务是平台面向行内的接口。两者分别管理，通过资源 API ID 关联；同一资源 API 可以封装为多个标准服务。数据源必须归属一个资源提供商。

## 2. 三个模块的职责

| 模块 | 管理内容 | 主要操作 | 不承担的职责 |
| --- | --- | --- | --- |
| 资源方管理 | 提供商登记信息、技术接入类型、独立处理应用 | 配置应用标识、应用路由地址和监听端口；生成工程及 Nacos 配置；查看生成记录 | 不配置各接口字段映射 |
| 数据资源接入 | 提供商 → 数据源 → 资源 API | 维护数据源基础地址与默认超时；保存 API 方法、地址、原始请求和响应样例；测试原始接口 | 不执行平台标准服务的字段映射、签名或加解密 |
| 标准服务开发 | 基于资源 API 的平台标准服务 | 选择来源资源 API；定义行内请求与响应；配置转换、安全处理和返回码；测试编排 | 不重新登记供应商原始接口，不替代资源方应用路由管理 |

服务发布与访问授权继续单独管理。测试是辅助工具，不构成上线决策的强制前置条件；上线仍需满足基本配置有效、应用路由存在等执行条件。

## 3. 应用路由与供应商接口地址

- **提供商应用路由地址**：平台可访问的提供商处理应用地址，配置在资源方管理。平台通过它穿透到外围系统。同一提供商下的数据源、资源 API 共用此路由。
- **应用监听端口**：Java 进程启动时监听的端口，通过生成的 Nacos 配置生效；不是一个额外的调用跳点。
- **供应商基础地址**：外围供应商服务的地址。数据源可覆盖默认地址，资源 API 可继承数据源或单独指定完整 URL。
- **内部服务路径**：Adapter 与 Gateway 在平台内部转发标准服务使用的 HTTP 路径。行内调用方在 XML 中指定服务编码，无需填写这个路径。

平台不能用供应商 URL 替代处理应用路由。缺少应用路由或应用未启动时测试失败，不回退到 Admin 直连供应商。

## 4. 两条不同的执行流程

### 原始资源 API 测试

```text
数据资源接入页面
  → Admin 读取资源 API 与提供商路由
  → 提供商应用 /internal/adapter/execute
  → 按资源 API 的方法、地址、超时发送原始请求
  → 供应商原始响应 → 页面
```

这里的原始请求是已保存的供应商请求样例，不经过标准服务字段转换、签名或加密流程。页面同时展示处理应用路由与供应商地址，以及成功调用的原始请求和原始响应；失败时展示错误信息，当前不保证完整保留上游非成功 HTTP 响应的原始报文。

### 行内标准服务调用

```text
行内系统
  → XML 写入 ESB 请求队列（生产底层 IBM MQ）
  → ESB Adapter 解析服务头与业务请求
  → 按 service_id 解析标准服务内部路径
  → Gateway 根据已发布服务路由到提供商应用
  → 提供商应用执行请求转换、配置的安全处理
  → 调用供应商接口
  → 提供商应用执行响应标准化
  → Adapter 封装标准 XML
  → 写入 ESB 响应队列 → 行内系统
```

正式入口由服务发布与调用系统授权控制。草稿编排测试和内部全链路测试是开发工具，不等同于正式入口授权。Kafka 日志保持结构化 JSON，不受行内 XML 报文格式影响。

**当前实现边界**：本地 ESB 仍使用进程内 `MockEsbQueue`，不是 IBM MQ 客户端。真实生产 MQ 的连接、请求/响应队列、关联标识、确认与重投策略仍需接入；本次调整没有宣称完成 IBM MQ 对接。

## 5. 开发操作顺序

1. 在资源方管理登记提供商，配置并部署该提供商的独立应用。
2. 在数据资源接入中，选择提供商并建立数据源。
3. 新增资源 API，填写方法、地址、原始请求与响应，保存为可用资源。新建后尚未保存的草稿不进入标准服务来源列表。
4. 可选执行原始接口测试。没有测试或测试失败，仍可继续标准服务开发。
5. 在标准服务开发点击“新增标准服务”，搜索并选择来源资源 API；也可从资源 API 页面创建。
6. 确认标准服务名称与服务编码。该编码对应 XML 的 `Service_Header/service_id`；内部路径默认生成，必要时展开内部转发配置修改。
7. 请求与响应初始继承资源 API 保存的样例。无需转换时可保持透传；需要转换时分别配置请求转换和响应标准化，以及安全处理和返回码映射。
8. 保存服务草稿，按需执行编排与链路测试。由开发人员决定发布，再配置调用系统授权。
9. 行内系统按平台接口文档向 ESB 发送 XML，并从响应队列接收 XML。

资源 API 保存后变更，不直接覆盖既有标准服务的开发契约。标准服务可手动“同步资源契约”到草稿，核对转换配置后再发布；已发布快照不会被草稿同步覆盖。

## 6. 主要存储与代码位置

| 对象 | MySQL / 配置位置 | 主要代码 |
| --- | --- | --- |
| 提供商及应用路由 | `data_provider`：`application_name`、`runtime_url`、`server_port` | Core 的 `InterfaceService` |
| 数据源归属与默认连接 | `data_source.provider_id`、基础地址及超时字段 | Core 的 `InterfaceService` |
| 原始资源 API | `resource_api`：方法、地址、请求/响应样例、保存状态 | Core 的 `InterfaceService` |
| 标准服务与来源关系 | `api_interface.resource_api_id`、服务编码、内部路径、请求/响应契约 | Core 的 `InterfaceService` |
| 字段与返回码规则 | `field_mapping`、`response_code_mapping` | Core 执行计划与转换模块 |
| 已发布执行快照 | `release_plan_snapshot`，运行时加载到应用内存 | Core 发布计划管理、提供商应用 |
| 应用启动配置 | Nacos 中对应应用的 Data ID | 提供商应用 `application.yml`、部署脚本 |
| 页面流程 | 不独立保存数据，调用 Admin 接口 | 前端 `src/App.vue` |
| 原始调用执行 | 从调用载荷读取提供商、数据源和连接配置 | SDK 的 `DraftAdapterExecutor`、`UpstreamClient` |
| XML 解析与响应封装 | ESB Adapter | `EsbXmlProtocol`、`EsbMessageAdapter` |

提供商分类和技术接入类型分别管理。HTTP 已有内置 JSON 对象连接器；数据库、平台微服务、Kafka 的配置和扩展接口不代表已实现完整通用连接器，详见《资源提供商级应用路由与接入类型改造》。
