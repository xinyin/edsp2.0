# 发布前验证与版本管理

更新日期：2026-10-09。

## 开发与发布流程

1. 在“上游能力接入”保存资源 API 的地址、请求和响应样例，并验证资源接口。
2. 在“标准服务开发”基于资源 API 创建标准服务。资源接口后续发生变更时，点击“同步资源契约”，明确将最新契约接入当前草稿。
3. 核对行内标准请求、请求映射、响应映射、返回码和安全策略，保存草稿。
4. 执行“发布前链路验证”。验证真实请求上游，当前草稿通过后才能进入发布环节。
5. 在“服务发布”上线，然后在“API 访问授权”配置调用系统的授权。
6. 可选执行“线上入口验收”：通过 XML → 模拟 ESB → Adapter → Gateway → 已发布数据服务检查线上入口及调用方授权。

上线不要求预先取得“线上入口验收”结果，因此不存在先上线才能满足上线条件的循环。

## 两种验证的边界

| 模式 | 实际执行路径 | 发布前是否必须 | 是否需要上线和调用方授权 |
| --- | --- | --- | --- |
| 发布前链路验证 | 保存的标准请求 → 管理端公共组件执行映射/安全策略 → 独立数据源应用 → 真实上游 → 返回码处理/响应标准化 | 是 | 否；仍由管理端访问权限保护 |
| 线上入口验收 | XML → ESB Adapter → Gateway → 已发布数据源应用 → 真实上游 → JSON | 否，作为可选验收 | 是 |

发布前验证当前使用管理端编排、独立数据源应用负责出站调用的草稿执行入口。它不会激活发布计划，也不改变线上路由。它不经过 ESB/Gateway，不能替代这两层的队列、路由、鉴权验收。链路记录中 Gateway 标为 SKIPPED，不再显示虚假的鉴权成功。

当前草稿出站入口沿用 HTTP POST/JSON 能力；其他供应商协议/方法以及应用专属插件仍需扩展对应执行入口，并验证与线上执行行为一致。本次修复不将业务草稿验证宣称为生产全链路验收。

## 资源契约同步

标准服务保存的是资源契约的草稿副本，不会因资源 API 被编辑而自动修改线上发布快照。

`POST /api/interfaces/{id}/sync-resource` 更新草稿的上游地址、路径、配置继承方式、超时、请求样例和响应样例。已有字段映射、返回码和安全策略保留。

- 请求方向没有映射，且标准请求样例仍等于旧上游请求样例时，标准请求样例一起更新，保持透传。
- 响应方向没有映射，且标准响应样例仍等于旧上游响应样例时，标准响应样例一起更新。
- 已定制的行内契约保持原样，由开发者调整与新上游契约之间的映射。
- 同步后清除当前草稿验证凭证，必须重新验证。
- 已发布路由、执行计划及其快照不受同步影响。

若资源接口将 `query_key` 改为其他字段，先同步资源契约，再核对标准请求与映射。不能通过删除上线校验来绕过供应商的必填约束。

## 校验与凭证

之前的 PLATFORM 测试只装载上游响应样例，可能出现样例测试通过、上线请求契约校验失败。现在 PLATFORM 表示真实的发布前业务链路验证，不再使用客户端提供的模拟响应。

验证与上线共同调用请求契约校验：字段映射和安全处理后的上游请求必须满足已保存的上游样例契约。目前仍是样例驱动规则：样例中的字段视为必填并检查 JSON 类型，尚不是带可选字段声明的完整 JSON Schema。

验证请求和映射必须与保存的草稿一致；未保存修改不能为数据库中的旧配置签发凭证。上游传输失败、返回码未匹配、业务结果为 ERROR、响应转换异常、验证期间配置改变时，都不能取得发布凭证。HIT 和配置为 MISS 的正常无数据结果可通过。

凭证存储在现有 `interface_validation_record` 表，类型为 `PRE_RELEASE`，绑定配置的 SHA-256 摘要。摘要包含请求、响应契约、映射、安全策略、结果码、地址、超时及候选版本等；排除状态、更新时间和已发布版本字段，避免仅因进入审批流程而失效。

每次保存草稿都会删除旧的 ORCHESTRATION/PRE_RELEASE 凭证。旧版基于模拟响应生成的 ORCHESTRATION 凭证不再满足上线条件。上线和审批通过时均检查 PRE_RELEASE 凭证。失败调用仍记录节点日志。

## 版本规则

旧实现中，保存映射、结果码、安全策略、连接配置分别执行 `current_version + 1`。因此 V1 → V6 可能只是保存了五次配置，并非上线了五次。

新规则将标准服务的 `current_version` 作为待发布版本：

| 操作 | current_version | published_version |
| --- | --- | --- |
| 创建服务、首次发布前反复保存 | 1 | 空 |
| 首次上线 | 1 | 1 |
| 编辑已上线 V1，首次保存 | 2 | 1 |
| 同一草稿再次保存映射/安全策略/返回码 | 2 | 1 |
| 验证通过并上线 | 2 | 2 |
| 再次编辑并保存 | 3 | 2 |

保存草稿使用 `COALESCE(published_version, 0) + 1`。验证不增加版本。保存次数不再作为发布版本数；是否需要重新验证由凭证与配置摘要控制，不能仅比较版本号。

历史已发布 V6 保留 V6，后续草稿为 V7，不重排历史发布记录。旧逻辑产生、尚未发布的 V6 草稿，在下一次保存或同步资源契约时归一为“已发布版本 + 1”（如已发布 V1，则为 V2）。未修改的历史草稿不在后台自动批量改号。

资源 API 的 `current_version` 仍表示资源配置修订次数，和标准服务发布版本是两种生命周期，不能用资源修订次数解释标准服务的上线次数。

## 部署与回归

没有新增数据库表或字段。需要更新管理后端并刷新前端；可使用 `jsnx-edsp-deployment/bin/reload-integration-stack.sh` 重载现有联调栈，此脚本不重置测试数据。

回归重点：上游字段变更后的契约同步；映射遗漏必填字段时验证直接失败；草稿验证真实调用数据应用且忽略模拟响应；上游错误与并发修改不能签发凭证；反复保存不跳版本；保存后凭证失效；已发布快照保持独立。
